# Практическая работа №5. Рефакторинг FastAPI-приложения

Приложение разделено по ответственности. API не изменился: `POST /tasks/` и `GET /tasks/`.

## Структура
```
practice5/
├── app/
│   ├── __init__.py
│   ├── main.py          # создание FastAPI-приложения, include_router()
│   ├── database.py      # DATABASE_URL, engine, get_session() (Dependency Injection)
│   ├── models.py        # SQLAlchemy-модель Task
│   ├── schemas.py       # Pydantic-схемы TaskCreate / TaskRead
│   └── routers/
│       ├── __init__.py
│       └── tasks.py     # GET /tasks/, POST /tasks/
├── tests/test_tasks.py  # проверка API на SQLite в памяти
├── docker-compose.yml, create_tables.sql, insert_data.sql   # PostgreSQL из практики №3
├── requirements.txt, requirements-dev.txt
└── README.md
```

## Запуск
```bash
docker compose up -d
docker compose ps
pip install -r requirements.txt
uvicorn app.main:app --reload          # запускать из корня practice5/
```
Swagger: http://127.0.0.1:8000/docs – должны быть `POST /tasks/` и `GET /tasks/`.

Пример тела POST:
```json
{ "title": "Изучить архитектуру FastAPI", "completed": false }
```
Ответ содержит созданную задачу с `id`; затем `GET /tasks/` возвращает её в списке.

Автотесты (не требуют PostgreSQL): `pip install -r requirements-dev.txt && pytest`.

## Контрольные вопросы
**1. Зачем разделять `models.py` и `schemas.py`?**
`models.py` описывает, как данные хранятся в БД (таблицы, столбцы, SQLAlchemy). `schemas.py` описывает, какие
данные принимает и отдаёт API (проверка входа, формат ответа). Это разные задачи: например, `id` не передаётся
клиентом при создании, а в БД он есть; в схеме ответа можно скрыть служебные поля. Изменение таблицы не должно
автоматически менять контракт API и наоборот.

**2. За что отвечает Router?**
Router группирует связанные HTTP-эндпоинты (здесь `/tasks`), принимает запросы, вызывает работу с БД через
`Session` и возвращает ответ. Он отвечает за HTTP-слой, а не за подключение к БД или описание таблиц.

**3. Зачем нужна `Session`?**
`Session` – рабочая сессия SQLAlchemy: через неё читаются и сохраняются объекты (`add`, `get`, `commit`).
Она управляет транзакцией и соединением с БД; через Depends на каждый запрос выдаётся своя сессия, которая
закрывается после ответа.

**4. Почему не стоит хранить всё приложение в `main.py`?**
В одном файле смешиваются подключение к БД, модели, схемы и эндпоинты: файл разрастается, его трудно читать,
тестировать и менять, а несколько человек конфликтуют при правках. Разделение «один компонент – одна ответственность»
позволяет менять один слой, не затрагивая остальные.

**5. Что произойдёт, если Router не подключить через `include_router()`?**
Приложение запустится, но эндпоинты роутера не будут зарегистрированы: в Swagger не будет `/tasks/`,
а запросы к ним вернут 404.

**6. Изменился ли API после рефакторинга?**
Нет. Остались те же пути и методы (`POST /tasks/`, `GET /tasks/`), те же входные и выходные данные.
Изменилась только внутренняя структура кода: код перенесён из одного файла в модули.
