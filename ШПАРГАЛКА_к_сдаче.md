## ПР1. Первый FastAPI (папка `practice01`)

```powershell
cd practice01

```

Покажи в браузере: http://127.0.0.1:8000 → `Hello Web`, `/docs` (Swagger), `/about`, `/users`, **`/info`** (индивидуальное задание: тема Pet Clinic), домашние `/hello`, `/contacts`, `/status`. Покажи `git log` в корне: коммит «Initial FastAPI project».

## ПР2. REST API в памяти (папка `practice02`)

```powershell
cd ..\practice02
..\.venv\Scripts\python.exe -m uvicorn main:app --reload
```

В Swagger (http://127.0.0.1:8000/docs) покажи по порядку:
1. `GET /pets` — список; 2. `GET /pets/1` — один (200), потом `GET /pets/999` — ошибка **404**;
3. `POST /pets` (Try it out → Execute, тело по умолчанию уже корректное) — **201 Created**;
4. `DELETE /pets/{id}` на созданном — сообщение об успехе; 5. то же для `/veterinarians`; 6. `GET /info`.
Затем **F12 → Network**: выбери запрос, покажи Method, Request URL, Status Code, Request Headers, Response Headers, Response Body.
Тесты: `..\.venv\Scripts\python.exe -m pytest` (6 passed). Скриншоты уже лежат в `practice02\docs\`.

**Что сказать:**
- **REST API** — ресурсы адресуются URL (`/pets/1`), действия задают методы: GET читает, POST создаёт, DELETE удаляет.
- **JSON** — текстовый формат данных. **Status Code** — результат: 200 успех, 201 создано, 404 не найдено, 422 неверные данные.
- **Pydantic** (`BaseModel`) проверяет входные данные сам: `age=-1` даст 422, и из моделей строится Swagger.
- **Request Headers** отправляет браузер (что принимает, формат тела), **Response Headers** — сервер (тип и размер ответа, дата).
- Данные лежат в обычных списках Python — после перезапуска сервера пропадают, БД будет в ПР3.

## ПР3. PostgreSQL в Docker + psycopg (папка `practice3`)

```powershell
cd ..\practice3
docker compose up -d
docker compose ps            # practice_db — healthy
..\.venv\Scripts\python.exe main.py
docker compose exec db psql -U student -d practice -c "SELECT * FROM pets ORDER BY id;"
docker compose down -v
```

Видно: подключение, все записи (6 питомцев), запись с id=3, добавление, удаление, таблица в исходном состоянии. Покажи `create_tables.sql`, `insert_data.sql`, `docker-compose.yml` (БД `practice`, пользователь `student`/`student`).

**Что сказать:** Docker запускает PostgreSQL в контейнере, скрипты `.sql` выполняются при первом старте. Запросы с данными пользователя **параметризованные** (`WHERE id = %s`, `(pet_id,)`), конкатенации нет: так защищаются от SQL-инъекций. Соединение закрывается в `finally`.

## ПР4. SQLAlchemy ORM (папка `practice4`)

```powershell
cd ..\practice4
docker compose up -d
..\.venv\Scripts\python.exe main.py
docker compose down -v
```

В консоли видны SQL-запросы (`echo=True`): `INSERT`, `SELECT`, `UPDATE`, `DELETE`. Покажи модель `Task` (`Mapped`, `mapped_column`), `Engine`, `Session`.

**Что сказать:** ORM превращает таблицу в Python-класс. `cursor.execute("SQL")` — я сама пишу SQL; `session.get(Task, 1)` — SQLAlchemy формирует SQL за меня, но он никуда не исчез, его видно в консоли. `Engine` — подключение к БД, `Session` — «рабочий сеанс» с объектами: `add`, `commit`, `delete`. В ПР4–5 таблица `tasks`, как в методичке; в ПР3 — `pets` по варианту.

## ПР5. Рефакторинг (папка `practice5`)

```powershell
cd ..\practice5
docker compose up -d
..\.venv\Scripts\python.exe -m uvicorn app.main:app --reload
```

В Swagger: `POST /tasks/` (создать), `GET /tasks/` (список). Покажи структуру `app/`: `main.py`, `database.py`, `models.py`, `schemas.py`, `routers/tasks.py`. Тесты: `..\.venv\Scripts\python.exe -m pytest` (5 passed). После сдачи: `docker compose down -v`.

**Что сказать (контрольные вопросы):**
1. **Зачем models и schemas отдельно:** `models.py` — как данные лежат в БД, `schemas.py` — что принимает и отдаёт API (например, `id` клиент не присылает).
2. **Router** — группа endpoints одной темы (`/tasks`), подключается в `main.py` через `include_router()`. Без `include_router` эндпоинтов в приложении не будет (404).
3. **Session** — сеанс работы с БД, выдаётся через `Depends(get_session)` (Dependency Injection).
4. **Почему не всё в `main.py`:** один файл разрастается, трудно читать и менять; «один компонент — одна ответственность».
5. **Изменился ли API:** нет, те же `POST /tasks/` и `GET /tasks/`; изменилась только структура кода.

## Если спросят «почему так»

- **Почему в ПР3 таблица `pets`, а в ПР4–5 `tasks`?** ПР3 по методичке «по вашему варианту» (Pet Clinic), а в ПР4–5 методичка прямо задаёт таблицу `tasks` и модель `Task`.
- **Откуда 404 в DevTools на POST?** Это пример проверки: в теле был `veterinarian_id: 0`, такого ветеринара нет, API вернул 404. Теперь пример в Swagger без этого поля, и POST даёт 201.
- **Где БД в ПР2?** Нет: по заданию данные в списках Python.
